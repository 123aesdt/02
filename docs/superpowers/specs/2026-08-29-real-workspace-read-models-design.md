# CountyFlow 真实工作区读模型与开发演示数据设计

**状态：** DESIGN APPROVED

**日期：** 2026-08-29

**选择：** 方案 A——真实只读 API、明确来源标记、非生产开发种子

## 1. 问题与证据

当前空白页并非统一的数据加载故障。前端在 API 模式下对系统总览、异常、运单、待复核、全局运行态和向量记忆显式返回 `NOT_EXPOSED`，后端只提供任务详情、任务级运行态和单个记忆事实读取，没有这些页面需要的有界列表契约。

2026-08-29 对正在运行的 Docker 开发环境进行只读核对：

- MySQL 有 1 个运单、1 个异常、3762 个调度任务、2906 个调度结果、2904 个审核结果和 3762 个运行线程；
- 任务状态中有 91 个 `REVIEW_REQUIRED`；
- Qdrant 的 `entity_resolution_memory` 集合有 7 条记录，向量维度为 128；
- 前端记忆页固定显示 2560 维，与当前 Docker 开发配置 `development-deterministic-128` 不一致。

因此根因由两部分组成：真实数据缺少安全的列表读模型；开发环境的运单与异常种子过薄，且部分页面把历史验收值当作当前运行值。

## 2. 目标与非目标

### 目标

1. 让系统总览、异常、运单、待复核、运行态和向量记忆在 API 模式下显示真实来源数据。
2. 所有查询有界、分页、权限受控，并只返回页面需要的安全字段。
3. 一键 Docker 开发环境幂等写入一组明确标识的演示运单和异常，生产环境永不注入。
4. 页面清楚区分 `LIVE`、`DEMO`、`EMPTY`、`STALE`、`UNAVAILABLE`，API 模式不回退本地 Mock。
5. 修正记忆维度、提供商和模型等运行口径，不再使用固定验收文案冒充当前状态。

### 非目标

- 不新增复核批准或拒绝动作；本轮只开放复核队列读取。
- 不伪造运行线程、检查点、调度结果或审核结果。
- 不返回 Redis 原始检查点、密钥、连接串、授权头或供应商敏感信息。
- 不改变异步调度主链路、幂等语义、Worker 消费或乐观锁规则。
- 不为多租户、区域或任务所有权虚构当前模型中不存在的字段。

## 3. 方案比较

### 方案 A：真实读模型 + 明确开发种子（采用）

后端从 MySQL/Qdrant 生成安全分页 DTO；前端只消费这些 DTO。开发种子只补业务入口所需的运单和异常，并通过编号前缀与响应来源字段标记为演示数据。优点是页面有内容且数据边界真实，缺点是需要新增窄接口和查询仓储。

### 方案 B：API 模式回退前端 Mock（拒绝）

实现最快，但页面状态会与数据库脱节，无法解释数据来源，也违反现有“API 模式不回退 Mock”的真实性规则。

### 方案 C：直接种入完整任务、调度、审核和运行线程（拒绝）

表面数据最丰富，但会伪造 Worker 执行结果，并产生缺失 Redis 检查点的孤儿运行线程。开发种子不得绕过真实异步处理链路制造成功任务。

## 4. 后端架构

新增单一用途的 `workspace_reads` 读模型模块：

```text
FastAPI route
  → require_permission
  → WorkspaceReadService
  → WorkspaceReadRepository (MySQL)
  → VectorMemoryReadRepository (Qdrant)
  → typed safe response
```

API 路由不直接导入 SQLAlchemy、Qdrant 客户端或供应商 SDK。服务只依赖窄协议；MySQL 和 Qdrant 适配器分别负责查询与 DTO 投影。

### 4.1 端点

| 方法与路径 | 权限 | 用途 |
|---|---|---|
| `GET /api/v1/workspace/overview` | `system:admin` | 六个产品域的真实数量、状态和来源摘要 |
| `GET /api/v1/orders` | `orders:read` | 运单列表、状态汇总和异常关联 |
| `GET /api/v1/anomalies` | `anomalies:read` | 异常列表、风险与处理状态汇总 |
| `GET /api/v1/reviews` | `dispatch:review` | `REVIEW_REQUIRED` 任务的只读复核队列 |
| `GET /api/v1/runtime/threads` | `runtime:read` | 全局运行线程安全摘要列表 |
| `GET /api/v1/memory/records` | `memory:read` | Qdrant 向量记忆安全浏览列表与集合元数据 |

所有列表默认 `limit=20`，允许范围 1–100。MySQL 列表使用稳定的 `before_id` 游标和确定性倒序；Qdrant 使用其 scroll offset，并把不透明游标编码为字符串。响应包含 `items`、`next_cursor`、`total` 和 `provenance`。

### 4.2 安全字段

- 运单：编号、状态、司机、车辆、路线、起点、终点、创建/更新时间、关联异常数和最近任务 ID。
- 异常：编号、运单编号、类型、严重度、描述、状态、上报时间、司机、车辆、路线和最近任务 ID。
- 复核：任务 ID、等待时间、异常风险/原因、车辆、原路线、最新 AI 调度建议和状态；不返回完整审计证据。
- 运行态：线程 ID、任务 ID、状态、当前节点、下一节点、状态版本、最后事件序号和更新时间；绝不返回原始检查点正文。
- 向量记忆：记忆 ID、司机、路线、异常类型、历史解决方案、创建时间、投影状态，以及集合实际维度、配置模型和安全提供商标签；不返回向量值。
- 总览：各域计数、健康状态、来源和目标路由；不返回记录明细。

### 4.3 错误语义

- 未认证返回 401，权限不足返回 403；
- 非法游标或筛选参数返回 422；
- MySQL 不可用返回有界 503；
- Qdrant 不可用时仅记忆端点返回 503，不影响其他工作区端点；
- 合法但无记录返回 200、空 `items` 和 `provenance=LIVE`，前端显示业务空状态而不是“接口未开放”。

## 5. 开发演示种子

`app.seed` 保持幂等，并在 `runtime_profile` 为 `local`、`test` 或 `docker-dev` 时补充约 10 个运单与对应异常。生产环境遇到演示种子入口时直接跳过。

演示编号使用稳定前缀，例如 `DEMO-ORDER-`、`DEMO-ANOM-`；API 由该受控前缀派生单条记录的 `is_demo`，列表同时返回 `DEMO` 或混合来源说明。种子只写 MySQL 业务输入和现有 Qdrant 示例记忆，不写完成任务、调度、审核或运行线程。用户通过真实调度入口提交后，任务仍由 Redis Streams 与 Worker 产生。

种子包含县域物流常见情境：暴雨湿滑、道路封闭、车辆故障、站点积压、运力不足和天气预警。司机、车辆、路线、起讫点和中文描述完整，可支持列表筛选与详情抽屉。

## 6. 前端数据流

新增类型化 `workspace-read-client`，API 模式下由页面 hooks 读取真实端点：

```text
route page
  → useWorkspaceRead(...filters)
  → typed API client
  → loading / ready / empty / forbidden / unavailable
  → metrics + table + drawer
```

- `/overview`：用真实域摘要替换六个“汇总未开放”徽标。
- `/anomalies`：展示真实汇总、筛选、分页表格和关联任务入口。
- `/orders`：展示真实运单、异常关联与最近调度任务。
- `/reviews`：替换占位页，展示只读待复核队列；不出现确认/拒绝按钮。
- `/runtime`：替换占位页，展示线程状态、节点、版本和任务详情入口。
- `/memory`：展示 Qdrant 实际记录及 128 维等运行元数据，不显示固定 2560/SiliconFlow 验收值。
- `/operations` 与 `/monitor`：复用运行线程摘要；监控实时指标缺失仍保留明确的陈旧/未开放语义，不编造数值。

Mock 模式继续用于隔离的前端演示和组件测试；API 模式绝不自动调用 Mock 服务。

## 7. 权限与审计

每个新增端点必须加入现有端点—权限契约测试，且只检查对应的具体权限。`system:admin` 仅保护管理员总览，不作为其他端点的通配符。列表读取记录安全访问审计时不得包含查询结果正文或敏感标识集合。

复核队列的可见性不代表复核动作授权；本轮没有动作路由。运行态列表仅提供摘要，任务级干预资格仍由现有线程详情和干预端点决定。

## 8. TDD 与验证

实现按以下 RED→GREEN 顺序推进：

1. MySQL 读仓储：分页、筛选、联表字段、稳定游标和演示来源。
2. Qdrant 读仓储：scroll、实际维度、安全负载和不可用错误。
3. API 契约：六个端点、权限、422/503、空列表和禁止敏感字段。
4. 开发种子：幂等、多样数据、生产跳过、不制造终态任务。
5. 前端客户端/hooks：真实请求、状态机、无 Mock 回退。
6. 六个页面：指标、表格、分页、详情和错误/空状态。

必须运行：

- `ruff check backend`
- 后端完整 `pytest` 与新增 API/仓储定向测试
- 前端 lint、完整单元测试和生产构建
- Docker MySQL/Qdrant 集成检查
- Playwright 验证 `/overview`、`/anomalies`、`/orders`、`/reviews`、`/runtime`、`/memory`、`/operations` 和 `/monitor`
- 1366×768 与 1920×1080 视口；检查控制台、框架错误层、空白、溢出和筛选/分页交互
- `git -c safe.directory=<workspace> diff --check`

## 9. 验收标准

1. 用户截图中的“汇总/列表接口尚未开放”在对应 API 页面不再出现。
2. 当前运行环境至少能看见 1 个真实运单、1 个真实异常、91 个真实待复核任务、运行线程和 7 条 Qdrant 记忆；重新初始化后能看到明确标识的开发演示业务记录。
3. 记忆页显示集合实际 128 维，不再显示固定 2560 维。
4. 所有列表有来源标识、加载、真正空、403 和 503 状态。
5. 没有静态 KPI 被标记为实时数据，没有 Mock 数据混入 API 模式。
6. 未新增复核写操作，未暴露原始检查点或向量，未改变异步生产链路。

## 10. 自审

- 无 `TBD`、`TODO` 或未决定数据口径。
- 真实数据与开发演示数据边界明确。
- 端点权限与现有 RBAC 一一对应。
- 新查询模块保持单一用途，API 层不直接接触数据库或 Qdrant。
- 开发种子不伪造任务执行结果，生产环境明确禁止。
- 页面范围与九张问题截图一致，不包含无关重构。

# 人工复核决定闭环设计

## 目标

让拥有 `dispatch:review` 权限的本地演示员工对 `REVIEW_REQUIRED` 任务执行真实的“批准”或“拒绝”，结果持久化到本地 MySQL，刷新页面后仍然有效，不接入企业数据。

## 产品行为

- 待复核表格新增“操作”列，提供“批准”和“拒绝”。
- 批准前显示中文二次确认；备注可选。
- 拒绝前显示中文二次确认；拒绝原因必填，长度 2–500 字。
- 提交期间禁用同一行操作；成功后刷新真实列表，已处理任务不再出现。
- 失败时保留任务并显示中文错误；并发重复处理明确提示“该任务已由其他人员处理”。
- 主管和系统管理员可操作；其他角色仍由 `dispatch:review` 权限边界拒绝。

## 后端契约

`POST /api/v1/reviews/{task_id}/decision`

请求：

```json
{"decision":"APPROVE","reason":"同意按安全绕行方案执行"}
```

或：

```json
{"decision":"REJECT","reason":"车辆状态信息不完整，需要重新评估"}
```

成功返回任务标识、决定、终态、复核人、决定时间和调度版本。不存在返回 404；任务已处理或不是待复核状态返回 409；非法请求返回 422；无权限返回 403。

## 持久化与并发

- MySQL 是唯一事实来源。
- 事务内锁定 `DispatchTask`，只允许 `REVIEW_REQUIRED` 转换为 `APPROVED` 或 `REJECTED`。
- 同一事务更新关联 `Dispatch`；其现有 `version_id_col` 负责并发版本检查，`StaleDataError` 统一转换为 HTTP 409。
- 每次成功决定追加一条 `AuditRecord`，`result` 为 `APPROVED` 或 `REJECTED`；`evidence_json` 只保存复核人标识、显示名、决定和时间，不保存令牌或密钥。
- 不修改订单，不触发 Worker，不同步执行 LangGraph；本轮批准表示“人工复核通过”，不伪造车辆已经实际执行。

## 安全与演示边界

- 身份只能来自服务端认证主体，前端不得提交或覆盖复核人。
- 演示账号和真实角色共用同一权限检查，不建立前端旁路。
- 所有文案优先中文；API 枚举和稳定错误码保留英文以便程序处理。

## 验收

- 服务、API、权限、并发和审计均有行为级测试。
- 前端覆盖批准成功、拒绝原因校验、409 和 403/服务错误反馈。
- Docker MySQL 中批准/拒绝后，待复核列表数量减少且刷新不恢复。

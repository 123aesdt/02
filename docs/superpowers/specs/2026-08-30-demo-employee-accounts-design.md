# 免密演示员工账号设计

## 目标

为 CountyFlow 的本地展示环境提供五个可持久化、可切换、无密码的演示员工账号。账号只承载虚构展示身份和角色权限，不接企业目录、邮箱、手机号或真实业务数据。

## 已批准的产品约束

- 创建五个独立账号，分别对应调度员、运营员、主管、审计员和系统管理员。
- 不设置密码，也不实现空密码登录。
- 账号仅用于展示；免密接口只允许 `local`、`docker-dev`、`test` 运行配置。
- `production` 不暴露账号列表和免密会话接口，统一返回 404。
- 浏览器只能提交员工编号，角色与权限必须由后端账号记录派生。
- JWT 继续使用现有短期开发会话签名、过期和注销撤销机制。
- 访问令牌只保存在前端内存，不写入 localStorage、sessionStorage 或 Cookie。

## 数据模型

新增 `demo_employee_accounts` 表：

- `employee_id VARCHAR(32)`：主键，稳定员工编号。
- `display_name VARCHAR(128)`：中文展示名称。
- `role VARCHAR(32)`：五种 CountyFlow 角色之一。
- `is_active BOOLEAN`：是否允许签发会话。
- `created_at`、`updated_at`：带时区的审计时间。

表中明确不包含密码、令牌、邮箱、手机号和企业标识。开发种子脚本幂等写入五个账号，已有账号仅补齐缺失记录，不覆盖人工停用状态。

## 后端边界

新增窄接口 `DemoEmployeeAccountRepository`，只提供“列出启用账号”和“按员工编号读取启用账号”。SQLAlchemy 细节封装在仓储实现内，API 路由只依赖 `DemoEmployeeSessionService`。

新增接口：

- `GET /api/v1/auth/demo-employees`：返回启用账号的员工编号、显示名称和角色，按员工编号排序。
- `POST /api/v1/auth/demo-session`：接收 `{ "employee_id": "CF-DEMO-001" }`，从服务端读取账号后签发短期 JWT。

未知、停用或格式无效的员工编号返回统一的 404，不泄露停用状态。非开发运行配置也返回 404，响应中不得出现 JWT、数据库连接信息或内部异常。

保留现有 `/development-session` 作为开发自动化兼容接口，但正式展示界面不再通过客户端提交角色来切换身份。

## 前端体验

开发 JWT + API 模式启动后，前端并行读取演示员工列表，不再自动接入管理员身份。顶部显示“选择演示员工”；选择账号后调用 `/demo-session`，成功后导航到该角色的默认工作区。

已登录状态显示员工姓名、中文角色和“演示身份”标识。切换账号会替换内存中的会话；退出会撤销当前 JWT、清空内存并回到账号选择状态。加载失败显示中文错误，不回退到静态角色或模拟权限。

## 安全与审计

- 免密能力由运行配置和开发 JWT 提供器共同启用，不能仅依赖前端隐藏。
- JWT 的 `sub` 使用员工编号，`name` 使用账号显示名称，`roles` 只包含数据库中的角色。
- 停用账号不能签发新会话；已签发会话继续服从现有短 TTL 和注销撤销机制。
- 前端不缓存账号会话令牌；刷新页面后重新选择演示员工。
- 所有文案明确标注“演示”，避免被误认为企业认证或真实员工数据。

## 验收标准

1. 数据迁移可创建账号表，开发种子可幂等生成五个账号。
2. 开发环境可列出五个账号并分别签发正确角色的 JWT。
3. 客户端无法通过修改请求把普通员工提升为管理员。
4. 停用、未知账号和生产环境都不能取得会话。
5. 前端可以选择、切换、退出五个员工身份，并按角色刷新导航和落地页。
6. 页面无密码输入框，令牌不写浏览器持久存储。
7. 后端、前端及 Docker 相关回归测试通过。
